## Scope completed

Implemented `docs/plan/M09-S03_TENANT_ISOLATED_RETRIEVAL_PLAN.md` (approved 2026-10-06, "ok implement"; Q1–Q8 as recommended). Backend and API only; the test-console screen comes in S08.

1. **ADR-019** (`Proposed`; your acceptance is part of this review):
   - vectors stored as PostgreSQL `real[]`, ranked in the application **after** a SQL tenant/approval filter;
   - no database extension;
   - move to pgvector when a tenant passes about 2,000 active chunks or p95 retrieval exceeds 50 ms.
2. **Provider-neutral embedding boundary:**
   - `IAiEmbeddingClient`;
   - OpenAI-compatible `POST /embeddings` client (Gemini today, others by configuration);
   - offline deterministic `FakeEmbeddingClient`.
   - **Same kill switch as chat:** while `Ai:Enabled` is off, nothing is sent.
   - **Configuration:** `Ai:Embeddings` (`gemini-embedding-001`, 768 dimensions, batches of 32) and `Ai:Retrieval` (thresholds 0.62 / 0.55, lexical weight 0.1, lexical thresholds 0.5 / 0.25, top 4, ≤ 3,000 characters), validated at start-up.
3. **Chunks with version metadata (`knowledge_chunks`):**
   - **Content:** tenant, document, version, chunk index, exact character range, content hash, optional vector with model and dimensions.
   - **Chunking:** about 800 characters with 100 overlap. It prefers paragraph breaks, then sentence ends (incl. `।`), then spaces, and never cuts inside a word or a Devanagari grapheme.
   - **Lifecycle:** chunks are created in the approval transaction, so lexical retrieval works immediately. Superseding or deleting a version removes its chunks in the same transaction.
4. **Indexing (`KnowledgeIndexingJob`):**
   - immediate per-version job after approval;
   - recurring sweeper `knowledge-indexing` every 5 minutes;
   - per-tenant reindex.
   - **The sweeper** embeds missing vectors, **re-embeds after a model or dimension change**, removes orphan chunks, and **retries failed storage purges** (closes the S02 assumption).
   - Jobs carry the tenant and run only for active tenants.
5. **Retrieval (`IKnowledgeRetrievalService`):**
   - **Order of operations:**
     1. tenant from trusted context;
     2. **SQL filter** to the Active version of non-deleted documents;
     3. one query embedding;
     4. cosine + lexical boost **on those candidates only**;
     5. thresholds;
     6. top 4 within the character budget.
   - **Returns:** `Confidence` High/Low/None, `Mode` Hybrid/LexicalFallback, and passages marked `untrusted` with a full citation (document id/title/category, version id/number, chunk index, character range, content hash).
   - **Lexical fallback:** if embeddings are unavailable (AI off, provider failure, not indexed yet, model changed), retrieval falls back to lexical ranking instead of failing.
6. **Suspicious-instruction flag:**
   - **Detection:** text that looks like instructions to the AI ("ignore previous instructions", "reveal your system prompt", "you are now…", "rules birsa"…) sets `hasSuspiciousInstructions` on the version at submission.
   - **Warn only:** the owner still decides, and approved content is always treated as data.
7. **API:**
   - `POST /v1/assistant/knowledge/search` (test console; read permission);
   - `POST /v1/assistant/knowledge/reindex` (write permission; 202);
   - the knowledge list gains `indexStatus` (`chunks`, `indexed`) and the version flag.
   - Antiforgery on both. OpenAPI/TS regenerated (additive).

**Deviations from the plan:**
- **D1:** `Mode` has `Hybrid` and `LexicalFallback` only. There is no separate `Semantic`, because the small lexical boost always applies in normal mode (Q7).
- **D2:** the index status shows `chunks` and `indexed` for the active version; pending = chunks − indexed.
- **D3:** the flag is named `hasSuspiciousInstructions` (the plan said `SuspiciousInstructionWarning`).
- **D4:** `KnowledgeDocumentVersion.MarkDeleted()` now **keeps** the original's storage key until the purge is confirmed (`ConfirmOriginalPurged()`), so the sweeper can retry it. The text is still cleared at once. The S02 unit test was updated to match.
- **D5 (test harness only):** the S02 assistant test host set `BackgroundJobs:ServerEnabled=false` through in-memory configuration. `Program.cs` reads that value before such configuration applies, so a Hangfire server actually ran inside those tests.
  - The new shared `AssistantTestHost` sets it as a host setting.
  - Its background tenant resolution now uses the real active-tenant rule.
  - Production code unchanged.
- **Not built (optional in the plan):** the live retrieval harness command. The thresholds are the starting values from the 2026-10-06 embedding probe (ADR-019) and are tuned in S08.

## Implementation design

- **Domain** (`Kreyora.Domain/Assistant/KnowledgeChunking.cs`):
  - the `KnowledgeChunk` entity;
  - `KnowledgeChunker` (deterministic spans with `Text == source[Start..End]`);
  - `KnowledgeTokenizer` (lowercase, Devanagari digits → ASCII, keeps combining marks, small stop-word list);
  - `SuspiciousInstructionDetector`.
- **Application:**
  - `Ai/AiEmbeddingContracts.cs`: embedding boundary;
  - `Assistant/AssistantContracts.cs`: retrieval, indexing and scheduler contracts, citation/passage/result records, index status.
- **Infrastructure:**
  - `Ai/EmbeddingClients.cs`: kill switch → fake or live; batched transport; strict response mapping (count, order by `index`, dimensions); logs without text.
  - `Assistant/KnowledgeIndexing.cs`: indexing service, Hangfire job, after-commit scheduler that never throws into the request.
  - `Assistant/KnowledgeRetrievalService.cs`: filter → embed → `Rank` (pure, unit-tested).
  - `KnowledgeService`: chunk create/remove on approve/supersede/delete, purge with retry, index status in the list.
- **Data flow:**
  - **Approve (one transaction):** remove the superseded version's chunks, add the new chunks, audit, commit. After commit, the index job is queued.
  - **Job:** embeds the chunks.
  - **Search:** SQL candidates, then scoring.
  - **Delete (one transaction):** mark versions deleted, remove chunks, audit, commit. Then the storage purge runs; on failure the key is kept and the sweeper retries.
- **Invariant:** retrieval correctness does **not** depend on chunk clean-up. The SQL join (`chunk.VersionId == document.ActiveVersionId`, version Active, document not deleted, the same tenant on chunk, version and document) is the guarantee. Clean-up is defense in depth.

**Integration tests (real HTTP + PostgreSQL, fake embedder, no network):**
- **Cross-tenant collision:** two shops with identical text and titles each retrieve only their own document. A query with injection text and the other shop's tenant/document/version IDs, plus those IDs and `topK: 50` in the body, still returns only the caller's passages, at most 4.
- **Approval state + filter before ranking:**
  - pending, rejected, superseded and deleted content is never returned;
  - **leftover chunks inserted directly** for a superseded version, and for another tenant, with text and vectors **identical to the query**, are never returned; only the lower-scoring active v2 passage comes back;
  - the sweeper then removes the leftover chunk.
- **Chunk lifecycle:** pending → no chunks; approve → chunks; supersede/delete → that version's chunks gone in the same request.
- **Confidence:** a blank query, an unrelated question and a shop with no knowledge all return `none` with no passages.
- **Malicious instructions:**
  - flagged at submission (a clean document is not flagged);
  - after approval, returned verbatim with `untrusted: true` and a citation;
  - the list shows the flag.
- **Citation traceability:** every passage equals `ContentText[charStart..charEnd]` of the cited version, its hash matches, and the budget (≤ 4 passages, ≤ 3,000 characters) holds.
- **Indexing:**
  - lexical right after approval;
  - immediate indexing is idempotent (1, then 0);
  - status `indexed == chunks`; mode becomes hybrid;
  - after a simulated model change, retrieval falls back until the sweeper re-embeds;
  - reindex re-embeds with the current model and dimensions.
- **AI disabled:** nothing embedded, `embeddingAvailable: false`, lexical answers still work.
- **Provider failure** at query and index time: lexical fallback, no errors.
- **Tenant-scoped jobs:** a job carrying the wrong tenant indexes nothing; the right tenant indexes all.
- **Permissions:** unauthenticated 401; missing CSRF 400; Viewer/Operator/Admin/Owner may search; Viewer/Operator reindex 403; Admin 202.
- **Storage purge retry:** during a storage outage, delete still succeeds, the text is cleared and the key is kept; the sweeper purges once storage recovers.

## Security and isolation review

- **Tenant isolation:**
  - the tenant comes only from trusted context; the search API accepts only query text;
  - the candidate SQL requires the same tenant on chunk, version and document, plus EF query filters;
  - the composite FK `(tenant_id, version_id)` ties every chunk to a version of the same tenant;
  - jobs carry the tenant and run only for active tenants.
  - All tested.
- **Approval state:** only the document's current Active version can be a candidate, and the filter runs **before** any scoring (tested with higher-similarity forbidden chunks; mutation-checked).
- **Prompt injection:**
  - passages are returned as `untrusted` data with citations;
  - instruction-like text is flagged to the reviewer at submission;
  - query text cannot change the tenant, filters or limits (tested);
  - S06 must wrap passages as quoted data.
- **Data handling:**
  - embedding obeys the kill switch, so with AI off (the default) no shop content is sent;
  - the free tier receives synthetic content only (ADR-018);
  - logs record provider, model, count, outcome and latency, never text or keys (tested);
  - vectors are derived content and are deleted with their versions;
  - deleted originals are purged with retry.
- **Abuse:** queries over 1,000 characters are cut; output is bounded (top 4, 3,000 characters); the sweeper embeds at most 500 chunks per tenant per run.
