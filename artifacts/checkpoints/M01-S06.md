## Implementation design

### Data flow

- **Order list**: `OrderClient.listOrders()` → client-side search and filtering by status/source/paymentStatus
- **Order detail**: `OrderClient.getOrder(id)` + `getOrderActivity(id)` + `PaymentClient.getPaymentAttempts(id)` + `InventoryClient.getInventory(variantId)` per item — all loaded in parallel
- **Action execution**: Pure UI simulation — `getAllowedActions` determines available buttons, clicking opens a confirmation dialog, "executing" appends a local `OrderActivity` to the timeline without any port mutation
- **Notifications**: Derived from order state via `getSimulatedNotifications()` — cosmetic entries based on order/payment/fulfilment status

### Key design decisions

1. **Three independent badges**: Order status, payment status, and fulfilment status are always displayed as separate badges (never merged), demonstrating their independent state machines per the prompt.
2. **Immutable financial snapshot**: The items table and totals section has no edit affordance — reflecting the requirement that the financial snapshot is immutable once an order is created.
3. **Simulated actions in UI layer**: Since ports are read-only and this is a demo, actions are entirely client-side. The confirmation dialog appends to a `localActivities` array that merges with the fixture timeline.
4. **Action policy as pure function**: `getAllowedActions` is a pure function with no side effects, making it easily testable (11 unit tests verify all transitions).
5. **Notification delivery status**: Cosmetic/derived — no full notification system. Entries are generated from order state to demonstrate the concept of delivery tracking.
6. **Native select elements for filters**: Used native `<select>` elements for order list filters instead of Radix Select to keep the implementation lightweight while maintaining accessibility.

## Risks and known limitations

1. **Client-side filtering**: The order list filters entirely on the client side after loading all orders. With real data, server-side filtering via `listOrders({ status, source, search })` would be needed.
2. **No real action persistence**: Simulated actions only append to a local React state array. Refreshing the page resets to fixture activities.
3. **Notification delivery is cosmetic**: No actual notification system exists. Entries are derived from order state to demonstrate the concept. A real implementation would need a notification service with delivery tracking.
4. **Confirmation dialog is custom**: Uses a simple overlay div rather than Radix Dialog for the action confirmation. This is functional but lacks the focus trapping and escape-key handling that Radix provides. Could be upgraded in a future pass.
5. **No pagination**: The order list loads all orders at once. The `PaginatedResult` cursor is available in the port but not used for pagination UI.
