## Scope completed

Implemented Milestone 06 Step 06 per the approved plan in `docs/plan/M06-S06_LIFECYCLE_AND_FAILURE_VERIFICATION_PLAN.md`:
1. **End-to-End Order Lifecycles:**
   - **Scenario 1 (COD Order Lifecycle):** Storefront checkout -> PendingConfirmation -> Confirm -> Prepare -> Dispatch -> Deliver + MarkCodCollected. Reconciled stock ledger at every step, confirmed outbox event emission, and verified complete chronological audit activity.
   - **Scenario 2 (Merchant-QR Order Lifecycle):** Storefront checkout -> AwaitingVerification -> Upload JPEG proof -> VerifyPayment -> Confirm -> Dispatch -> Deliver. Verified proof upload validation, status transition to `ProofSubmitted`, verification to `Verified`, and order completion.
   - **Scenario 3 (Merchant-QR Rejection & Restock):** Storefront checkout (3 units on hand, 2 ordered -> 1 available) -> Proof uploaded -> Operator rejects proof with required reason -> Operator cancels order -> Automated restock committed (`StockMovementType.OrderRestock`) -> Stock ledger verified exactly restored (3 on hand, 0 reserved, 3 available) -> Payment attempt expired.
2. **Concurrency, Collisions & Idempotency:**
   - **Scenario 4 (Optimistic Concurrency & 409 Conflict):** Operator A & B read version $V_1$. Operator A confirms -> version advances to $V_2$. Operator B attempts confirm with stale $V_1$ -> rejected with HTTP `409 Conflict`. Database verified unaltered by stale request.
   - **Scenario 5 (Concurrent Terminal Collision):** Parallel execution of conflicting terminal actions (Cancel vs Dispatch) on the same order. Exactly one operation wins with HTTP 200; the other fails with HTTP `409 Conflict`. Stock ledger verified fully consistent with no orphaned reservations or double restocks.
   - **Scenario 6 (Idempotency Replay & Key Conflicts):** Replay identical action with same `Idempotency-Key` returns cached result with `WasReplayed: true` and zero duplicate side-effects. Replay of differing payload with same `Idempotency-Key` rejected with HTTP `409 Conflict`.
3. **Notification Resilience & DLQ:**
   - **Scenario 7 (Bounded Retries, Dead-Lettering & Manual Replay):** Notification delivery against simulated failing provider records Attempt 1 -> 30s backoff enforced (`NextRetryAt > Now`) -> Advance clock -> Attempt 2 fails -> Advance clock -> Attempt 3 fails -> Notification transitions to `DeadLettered` with timestamp. Operator authorizes manual replay via `ReplayAsync` -> Status reset to `Pending` -> Subsequent run with operational provider delivers successfully. Contact PII redacted throughout.
4. **Security, Tenancy & Immutability:**
   - **Scenario 8 (Multi-Tenant Isolation):** Orders, payment proofs, and notification records created in Tenant A. Tenant B attempts listing, detail queries, activity queries, notification queries, action execution, and proof retrieval -> All return `404 Not Found` with zero cross-tenant leakage.
   - **Scenario 9 (Immutable Order Snapshot Invariant):** Order placed with snapshot price (Rs. 1,000) and delivery fee (Rs. 100). Catalog product title changed, variant price increased to Rs. 3,500, and delivery rule fee increased to Rs. 450. Order detail query verifies historical order retains original Rs. 1,000 unit price, original line item titles, and original Rs. 100 delivery fee.

- **Authentication/authorization impact:** Verified role-based enforcement: only authorized roles (`OrdersWrite`, `PaymentsManage`) can execute mutations; non-authorized roles receive 403 Forbidden.

- **Secret/PII/logging impact:** Verified customer recipient contact information (phone number / email) is redacted (`+97798****0010`) in notification listings, summaries, and activity logs.
- **Abuse/idempotency/concurrency impact:** Verified optimistic concurrency via PostgreSQL `xmin` prevents lost updates (HTTP 409 Conflict). Verified idempotency keys prevent duplicate processing and prevent conflicting payload replays. Verified concurrent terminal collisions (cancel vs dispatch) safely resolve with exactly one winner and zero stock ledger leakage.
