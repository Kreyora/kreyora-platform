## Scope completed

Exposed the approved catalog, inventory, reservation, and protected-media capabilities through versioned, tenant-context and policy-protected controllers. Regenerated the OpenAPI snapshot and TypeScript contract from a live local API. Replaced the seller catalog/inventory read adapters and the previously simulated product, media, and stock-adjustment writes with API-backed implementations. Fixture mode remains the deliberate no-`NEXT_PUBLIC_API_URL` mode; an API failure is not replaced with fixtures.

Catalog collection filters remain a fixture-only UI capability because collections do not yet exist in the M04 backend model. The real catalog endpoint implements server-side search, publication-status filtering, and opaque cursor pagination.

## Implementation design

- **Components/modules changed:** Catalog, inventory, and media controllers; catalog cursor-query contract/service; protected private-media read service; generated frontend API contract; typed catalog/inventory ports and real/mock adapters; seller product editor and inventory adjustment UI.
- **Runtime or data flow:** authenticated browser request + verified selected workspace → tenant/policy-protected controller → application service → PostgreSQL/private storage. Catalog list queries are server filtered/paged. Mutations obtain the existing anti-forgery token, send it with the verified workspace header, and render the server-returned product or balance rather than recalculating business values locally.
- **Key invariants enforced:** tenant context is required before dispatch; catalog/inventory authorization remains service and endpoint enforced; product/inventory concurrency tokens are returned and supplied on subsequent updates; stock changes use the append-only ledger; media content is authenticated, tenant scoped, and streamed from private storage without exposing object keys.
- **Compatibility with prior work:** uses the accepted M04-S01–S04 services, DTOs, audit behavior, and media storage contract. No database migration was required.

## Security and isolation review

- **Authentication/authorization impact:** all controller actions require the established catalog/inventory read or write policies and `RequireTenantContext`; browser writes include the anti-forgery token.
- **Tenant-isolation impact:** no tenant identifier is accepted as route/body authority. Query filters/service ownership checks and tenant-scoped media service remain in force. Dedicated endpoint tests verify missing tenant context is rejected before dispatch.
- **Secret/PII/logging impact:** no credentials, object keys, local paths, or signed provider URLs are returned to the browser.
- **Abuse/idempotency/concurrency impact:** create/adjust/reservation APIs retain their existing idempotency semantics. Product and balance mutation paths send server concurrency versions and surface server failures rather than applying speculative values.

## Reviewer procedure

1. Start the local stack: `docker compose up --build`.
2. Start the seller web app with `NEXT_PUBLIC_API_URL=http://localhost:5001` and sign in as an Owner or Operator with a selected workspace.
3. Create a product with its first variant. Confirm the product appears in the catalog and the API owns its returned state/version.
4. Edit title/description/slug, upload a JPEG/PNG/WebP image, and remove it. Confirm the media list changes only after API success and that `/v1/media/{id}/content` rejects a different tenant.
5. On the inventory page, add a positive receipt and a negative correction with a reason. Confirm the displayed balance and ledger come from the server and a Viewer cannot mutate.
6. Check catalog search/status filters and cursor behavior through `/v1/catalog/products?search=...&pageSize=...`.
7. Run the verification commands in the table above if any local configuration changes.
