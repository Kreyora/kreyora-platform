## Implementation Design

- **Components/modules changed:**
  - `Kreyora.Domain`: Added `Payments/PaymentEnums.cs`, `Payments/PaymentProof.cs`, `Payments/PaymentAttempt.cs`, `Storefront/StorePaymentConfiguration.cs`.
  - `Kreyora.Application`: Added `Payments/PaymentContracts.cs`, modified `Orders/OrderContracts.cs`.
  - `Kreyora.Infrastructure`: Added `Payments/PaymentService.cs`, `Payments/StorePaymentConfigurationService.cs`, configurations `PaymentAttemptConfiguration.cs`, `PaymentProofConfiguration.cs`, `StorePaymentConfigurationConfiguration.cs`, migration `AddPaymentDomain`. Updated `AppDbContext.cs`, `OrderCreationService.cs`, `OrderOperationService.cs`, `DependencyInjection.cs`.
  - `Kreyora.WebApi`: Added `Controllers/PaymentController.cs`, `Controllers/StorePaymentConfigurationController.cs`.
  - `Kreyora.UnitTests`: Added `Domain/PaymentAttemptTests.cs`, `Domain/PaymentProofTests.cs`, `Domain/StorePaymentConfigurationTests.cs`.
  - `Kreyora.IntegrationTests`: Added `Payments/PaymentServiceTests.cs`, `Payments/StorePaymentConfigurationServiceTests.cs`.
- **Runtime or data flow:**
  - Order Created -> `OrderCreationService` creates `Order` + initial `PaymentAttempt` in same transaction.
  - Merchant QR -> Customer initiates proof upload (`PaymentService.InitiateProofUploadAsync`) -> uploads file stream (`CompleteProofUploadAsync`) validating binary signature -> stores in private object storage -> marks proof `Ready` -> transitions `PaymentAttempt` to `ProofSubmitted`.
  - Seller Verifies -> `OrderOperationService.ExecuteActionAsync(VerifyPayment)` -> demands `PaymentsManage` -> checks concurrency (`xmin`) & idempotency -> marks `Order.PaymentStatus = Paid` -> marks `PaymentAttempt.Status = Verified` recording actor/timestamp/provider reference -> appends audit event.
  - Seller Rejects -> `OrderOperationService.ExecuteActionAsync(RejectPayment, reason)` -> marks `Order.PaymentStatus = Failed` -> marks `PaymentAttempt.Status = Rejected` recording actor/timestamp/reason -> appends audit event.
  - COD Collection -> Dispatched/Delivered order -> `OrderOperationService.ExecuteActionAsync(MarkCodCollected)` -> marks `Order.PaymentStatus = Paid` -> marks `PaymentAttempt.Status = Collected` recording actor/timestamp/provider reference -> appends audit event.
- **Key invariants enforced:**
  - No client input alone can mark payment paid; only authorized seller actions can do so.
  - At least one payment method (COD or Merchant QR) must remain enabled for any store.
  - Merchant QR instructions cannot contain HTML markup (`<` or `>`).
  - Payment proof upload requires supported format (`JPEG`, `PNG`, `WebP`, `PDF`) with genuine binary header signatures.
  - Verification and rejection decisions on `PaymentAttempt` are immutable once set.
  - All payment state mutations write structured append-only audit events.
  - Strict tenant isolation across all entities, queries, and storage keys.
- **Compatibility with prior work:**
  - Completely backward-compatible with M01–M05 database schemas and M06-S01 state transition policies.
  - Zero model drift reported by EF Core.

## Security and Isolation Review

- **Authentication/authorization impact:**
  - `PaymentController.GetPaymentAttempts` and `GetProofContent` require `PaymentsRead`.
  - `PaymentController.InitiateProofUpload` and `CompleteProofUpload` require `OrdersWrite`.
  - Verification, rejection, and collection actions require `PaymentsManage` (Owner and Admin only).
  - `StorePaymentConfigurationController` requires `StorefrontRead` (GET) and `StorefrontWrite` (PUT) with CSRF protection.
- **Tenant-isolation impact:**
  - All new entities (`PaymentAttempt`, `PaymentProof`, `StorePaymentConfiguration`) implement `ITenantOwned`.
  - Query filters applied in `AppDbContext`.
  - Cross-tenant tests verified that Tenant B cannot access or initiate actions on Tenant A's payments or store configurations.
- **Secret/PII/logging impact:**
  - No secret tokens or gateway credentials used.
  - Audit metadata contains only non-sensitive identifiers and state names.
- **Abuse/idempotency/concurrency impact:**
  - Proof uploads validate content-type and file magic byte signatures, with strict file size limits and expiry timestamps.
  - Concurrency tokens (`xmin`) and idempotency fingerprints protect order state transitions.
