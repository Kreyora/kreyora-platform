## Implementation Design

- **Components/modules changed:**
  - `Kreyora.Domain`: Added `Notifications` namespace with aggregate root, child entity, enums, and retry policy.
  - `Kreyora.Application`: Added `Notifications` contracts, DTOs, options, and `PiiRedaction`.
  - `Kreyora.Infrastructure`: Added `Notifications` services, template registry, dev sink provider, Hangfire recurring jobs, entity configurations, and migration.
  - `Kreyora.WebApi`: Added `NotificationsController` with policy-based authorization and anti-forgery protection.
  - `Kreyora.UnitTests` & `Kreyora.IntegrationTests`: Added comprehensive unit and real PostgreSQL test suites.
- **Runtime or data flow:**
  1. Business actions in `OrderCreationService` or `OrderOperationService` commit canonical order changes, audit events, and append `OutboxMessage`s in a single database transaction.
  2. `OutboxNotificationProcessorJob` runs periodically for each active tenant via `ITenantJobRunner`, queries unprocessed outbox records, consults `INotificationTemplateRegistry`, extracts customer contact info from the order, creates `NotificationRequest` with a deterministic idempotency key (`{messageId}:{templateCode}:{channel}`), and marks `OutboxMessage.ProcessedAt = now`.
  3. `NotificationDeliveryJob` runs periodically for each active tenant, queries pending/retryable `NotificationRequest`s, renders template data from the event/order, and calls `INotificationDeliveryProvider.DeliverAsync(...)`.
  4. In development, `DevelopmentNotificationProvider` writes rendered output and redacted contact info to `notification_delivery_logs`.
  5. If delivery fails, `NotificationDeliveryAttempt` records the redacted error, and `NotificationRequest` is scheduled for retry with exponential backoff. If max attempts are exhausted, the notification transitions to `DeadLettered`.
  6. An authorized Owner or Admin can inspect dead-lettered notifications and issue a manual replay request (`POST /v1/notifications/{id}/replay`), which resets the attempt count, transitions the notification to `Pending`, and records a `notification.replay` audit event.
- **Key invariants enforced:**
  - **Outbox durability & idempotency:** Outbox messages are marked processed, never deleted. Duplicate processing of identical outbox events is deduplicated via the unique index on `(tenant_id, idempotency_key)`.
  - **Tenant isolation:** Every notification entity carries `TenantId`, global EF query filters enforce tenant isolation, and cross-tenant access returns 404.
  - **PII redaction:** Customer contacts (email/phone) are redacted in API summaries, details, logs, and development sink outputs.
  - **Bounded retries & DLQ visibility:** Notifications fail up to `MaxAttempts` before becoming `DeadLettered` with full error diagnostic history.
  - **Audited replay:** Manual replay requires Owner or Admin role and appends an immutable `AuditEvent`.

## Security and Isolation Review

- **Authentication/authorization impact:**
  - Viewing notifications requires `TenantPermissions.OrdersRead`.
  - Viewing dead-letter queue requires `TenantPermissions.OrdersRead` and Owner or Admin role.
  - Replaying notifications requires `TenantPermissions.OrdersWrite` and Owner or Admin role.
- **Tenant-isolation impact:**
  - All notification entities implement `ITenantOwned` with tenant verification on save.
  - Global EF query filters isolate data per tenant. Cross-tenant reads and replays return 404.
- **Secret/PII/logging impact:**
  - Customer contact details (email and phone) are masked via `PiiRedaction` in all API responses, logs, and development delivery records.
  - Raw contact info is only used internally by the delivery provider during dispatch.
- **Abuse/idempotency/concurrency impact:**
  - Idempotency verified: re-processing outbox messages does not duplicate notifications. Replaying notifications requires an `Idempotency-Key` header.
  - Concurrency token (`xmin`) protects `NotificationRequest` against concurrent mutations.

## Decisions and Assumptions

- **Code-defined templates:** Email templates are defined in `NotificationTemplateRegistry` with compile-time rendering. No external template engine or database management required for MVP.
- **Development provider safety:** `DevelopmentNotificationProvider` records rendered output in the `notification_delivery_logs` table for developer verification without contacting external mail/SMS providers.
- **Two-phase job design:** Separate Hangfire recurring jobs for outbox message ingestion (`OutboxNotificationProcessorJob`) and notification dispatch (`NotificationDeliveryJob`) ensure independent retry limits and failure isolation.
