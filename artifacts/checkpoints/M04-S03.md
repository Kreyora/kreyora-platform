## Implementation design

- **Components/modules changed:** Inventory domain, Application contracts, Infrastructure inventory service/mappings, EF migration, Hangfire composition, tests, ADRs, milestone/context records.
- **Runtime or data flow:** A reserve locks the current tenant's inventory row under a serializable transaction, expires due holds for that row, validates availability, increments `ReservedQuantity`, creates an active reservation and append-only command record, audits, then commits. Release decrements reserved stock. Commit decrements reserved and on-hand stock and writes an immutable `ReservationCommitted` ledger movement linked to the reservation.
- **Key invariants enforced:** `Available = OnHand - Reserved`; reserved cannot exceed on-hand; only active reservations transition; committed stock is represented in the ledger; idempotency keys replay an existing accepted reservation command; tenant filters, tenant-inclusive foreign keys, verified contexts, and row locks prevent cross-tenant or oversell writes.
- **Compatibility with prior work:** Existing M04-S02 adjustment movements retain null reference fields; the migration is additive. The API, generated client, frontend, fixtures, and catalog behavior are unchanged.

## Security and isolation review

- **Authentication/authorization impact:** Seller reservation writes require `InventoryWrite`; reads require `InventoryRead`; PlatformSupport remains read-only. Expiry requires a verified durable tenant context rather than a user header.
- **Tenant-isolation impact:** Reservation and command tables are tenant-owned, query-filtered, write-enforced, and related through tenant-inclusive composite foreign keys. Lock queries explicitly predicate by current tenant.
- **Secret/PII/logging impact:** No secret or customer data added. Audit metadata contains only IDs, quantity, source, and automated-expiry marker.
- **Abuse/idempotency/concurrency impact:** Per-operation idempotency records prevent duplicate side effects. Serializable transactions and `FOR UPDATE` locking define one availability boundary per inventory item.
