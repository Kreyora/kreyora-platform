## Implementation design

### Data flow

All pages use the existing client port architecture:
- `useClients()` provides `catalog` (CatalogClient) and `inventory` (InventoryClient) instances
- `useSession()` provides `effectiveRole` for role-aware rendering
- Data fetched via `useEffect` with cleanup to prevent state updates on unmounted components

### Key design decisions

1. **Responsive product list**: Desktop uses a full table with sortable columns; mobile uses cards with product title, status badge, variant count, and price range. Both use the same filtered dataset.
2. **Variant-to-product mapping**: The low-stock page needs to link to `/catalog/[productId]/inventory`, but `InventoryItem` only contains `variantId`. Solved by fetching the product list in parallel and building a `variantId → productId` mapping.
3. **ProductForm component**: Shared between create and edit pages. The `isEdit` flag controls whether variants/media sections appear and whether the slug auto-generates from the title.
4. **Radix Tabs**: Used for the edit product page to provide accessible tab navigation between Details, Variants, Media, and Inventory sections.
5. **Delete confirmation**: Uses a simple modal overlay rather than Radix Dialog, since it's a simulated action. The confirmation is dismissed by either button.
6. **Stock adjustment success**: Uses local state with a 3-second auto-clear for the success message.
7. **Badge variant mapping**: Movement types and reservation states are mapped to badge variants using constant records for consistent semantic coloring.

## Risks and known limitations

1. **No server-side rendering**: All catalog/inventory pages are client-side (`"use client"`). SSR with data fetching will be introduced when the backend is implemented.
2. **No pagination**: Product list shows all products. Cursor-based pagination from `listProducts` is available but not exercised with 5 fixture products.
3. **No image uploads**: Media section shows placeholder boxes. Actual file upload will require backend infrastructure.
4. **No real persistence**: All save/delete/adjust operations are simulated with timeouts and local state.
5. **Slug collision detection**: Auto-generated slugs don't check for uniqueness — the backend will enforce this.
