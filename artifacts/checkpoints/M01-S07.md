## Implementation design

### Data flow

- **Inbox list**: `ConversationClient.listConversations()` → client-side filtering by state, channel, search
- **Conversation detail**: `ConversationClient.getConversation(id)` + `getMessages(id)` + `IntegrationClient.getHealth(connectionId)` + `AIClient.getActionTraces(id)` — loaded in parallel, health load gracefully fails for missing connections
- **Integration list**: `IntegrationClient.listConnections()` → rendered as cards
- **Integration detail**: `IntegrationClient.getConnection(id)` + `getWebhookEvents(id)` — loaded in parallel
- **Assistant policy**: `AIClient.getAssistantConfig(tenantId)` — read-only display
- **Knowledge**: `AIClient.listKnowledge(tenantId)` — lifecycle actions mutate local state only
- **Console**: `AIClient.getActionTraces(fixtureConvId)` — used as source for pre-canned bot responses and tool traces
- **History**: `AIClient.getActionTraces(fixtureConvId)` — displayed as expandable trace log

### Key design decisions

1. **Takeover invariant**: When human takes over, `automationActive` toggles to false, "Bot Paused" badge appears, and the staff composer becomes available. When released, automation resumes and composer hides. Viewer role sees no takeover/compose controls.
2. **Staff composer as local state**: Messages sent via the composer are appended to a `localMessages` array that merges chronologically with fixture messages. No port mutation.
3. **Provider health on conversation**: The detail page loads `getHealth(connectionId)` to show the channel's operational status. This gracefully handles missing connections (WhatsApp/Instagram connections not in fixtures).
4. **Webhook replay simulation**: Clicking Replay on a failed event marks it in a local `replayedIds` set, changing the button to "Replayed" text. No real replay.
5. **Knowledge lifecycle**: Status changes are tracked in a local `localStatuses` map, allowing the UI to show approve/reject/archive transitions without port mutations.
6. **Sub-navigation pattern**: All four assistant pages share a consistent tab-style sub-navigation with the active page highlighted.
7. **Fixture-based console**: The test console uses the single fixture AI action trace to provide a deterministic bot response, showing the same tool-trace data regardless of user input.

## Risks and known limitations

1. **Missing fixture connections**: WhatsApp and Instagram conversations reference connection IDs (`conn-whatsapp-namaste`, `conn-instagram-namaste`) that don't exist in the channel connections fixture (only Facebook exists). The health load gracefully fails via try/catch.
2. **Single AI trace**: Only one AI action trace exists in fixtures (`conv-facebook-001`). The console and history pages always load this trace. A real implementation would have many traces across conversations.
3. **No real takeover protocol**: The takeover/release is purely local state. A real system would need server-side ownership management, websocket updates, and conflict resolution.
4. **Replay/reconnect are cosmetic**: These actions show visual feedback but perform no real operations. The reconnect button only appears for disconnected/error status, which doesn't occur in current fixtures (Facebook is connected).
5. **Knowledge lifecycle is local**: Document status changes don't persist across page reloads. The fixture documents are always "approved."
6. **Console response is static**: Regardless of user input, the test console always returns the same fixture response. A real implementation would involve actual AI model invocation.
