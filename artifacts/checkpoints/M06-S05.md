## Implementation design

- **Components/modules changed:**
  - `Kreyora.Application`: `OrderContracts.cs`
  - `Kreyora.Infrastructure`: `OrderQueryService.cs`, `DependencyInjection.cs`
  - `Kreyora.WebApi`: `OrdersController.cs`
  - `Kreyora.IntegrationTests`: `SellerOrderWorkspaceIntegrationTests.cs`
  - `apps/web`: `orders/[id]/page.tsx`, `orders/page.tsx`, `order-client.ts`, `payment-client.ts`, `api/order-client.ts`, `api/payment-client.ts`, `mock-order-client.ts`, `mock-payment-client.ts`, `client-provider.tsx`, `orders.test.tsx`
- **Runtime or data flow:**
  - Order list query -> `GET /v1/orders` -> `OrderQueryService.ListOrdersAsync` -> filters applied to tenant `AppDbContext.Orders` -> mapped to `OrderSummaryItem` with PostgreSQL `xmin` row version.
  - Order detail query -> `GET /v1/orders/{id}` -> `OrderQueryService.GetOrderDetailAsync` -> loads order, items, payments, delivery -> mapped to `OrderDetailItem`.
  - Allowed actions -> `GET /v1/orders/{id}/actions` -> server checks domain rules across order status, payment status, and fulfilment status.
  - Action execution -> `POST /v1/orders/{id}/actions` -> `OrderOperationService` verifies row version -> applies domain transition -> saves changes & creates outbox events. If version mismatch occurs, throws `DbUpdateConcurrencyException`, returning HTTP `409 Conflict`.
  - Frontend catches HTTP `409 Conflict` -> renders Version Conflict banner with "Refresh Order" button to re-fetch latest state.
- **Key invariants enforced:**
  - Strict tenant isolation: every query and command scopes to `TenantContext.TenantId`.
  - Server authority: actions, financial calculations, totals, and versions are server-evaluated and authoritative.
  - Concurrency safety: PostgreSQL `xmin` row version passed on every state transition; stale writes rejected with 409 Conflict.
  - Role-based authorization: `OrdersWrite` / `PaymentsManage` policies enforced; viewer role rejected with 403 Forbidden.

## Security and isolation review

- **Authentication/authorization impact:**
  - Endpoints require authentication and tenant context.
  - Mutations (`POST /v1/orders/{id}/actions`) require `OrdersWrite` or `PaymentsManage` policy authorization.
  - Viewer role is strictly restricted server-side (HTTP 403 Forbidden).
- **Tenant-isolation impact:**
  - All queries in `OrderQueryService` filter by `tenantAccessor.TenantId`.
  - Integration test `ListOrders_EnforcesTenantIsolation` explicitly verifies zero cross-tenant leakage.
- **Secret/PII/logging impact:**
  - Customer contact details are redacted in notification logs (`recipientContactRedacted`).
  - No customer secrets or payment credentials logged.
- **Abuse/idempotency/concurrency impact:**
  - Mutations require `Idempotency-Key` header and CSRF token.
  - Optimistic concurrency verified via `xmin` row version check; concurrent modifications result in HTTP 409 Conflict.
