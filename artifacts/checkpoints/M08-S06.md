1. **Backend enablers (Q1).**
   - **Job scheduling:**
     - Hangfire recurring sweepers `webhook-processing` and `outbound-delivery` run every minute.
     - Webhook ingress enqueues processing immediately after commit, for new events only, on both ingress paths.
     - Staff and automation replies enqueue delivery immediately after commit.
     - Closes the pre-existing M07 gap where these jobs were registered in DI but never scheduled.
   - **Assignee directory:** `GET /v1/conversations/assignees` (`conversations.read`). It returns active members of the current workspace, with display name and role only (no email).
   - **`MessageItem.deliveryFailureCode`:** for failed outbound messages, the provider error code of the latest delivery attempt (e.g. `delivery_unconfirmed`, `window_closed`).
   - **Development-only E2E seed** (`Development:Seed:E2ePersonas=true`):
     - Admin, Operator and Viewer personas.
     - A Simulator connection with a run-scoped signing secret.
     - Three conversations: two fresh, one 8 days old (outside the window).
2. **Frontend data layer.**
   - A typed `ConversationClient` port with an API adapter, and a separate mapping module from generated OpenAPI shapes. Enums are widened because the wire format is camelCase strings.
   - Writes send the tenant header and CSRF token; replies also send `Idempotency-Key`.
   - Full demo-adapter parity.
   - Adapter selection: API when `NEXT_PUBLIC_API_URL` is set, otherwise demo.
   - Denial copy is keyed on stable `urn:kreyora:problem:<code>` codes.
3. **Live refresh (Q2):** polling.
   - Open conversation every 5 s; list every 15 s.
   - Paused while the tab is hidden.
   - Exponential backoff up to 60 s on failures, with a stale/reconnecting banner.
4. **Inbox list.**
   - All / Unread / Assigned-to-me views, a status filter, Load more, and a Refresh button.
   - Loading, empty, filtered-empty, error and stale states.
   - Search and channel filters only in demo mode, because the API has no free-text search yet.
   - Demo notice.
5. **Conversation view.**
   - **Timeline:** customer, staff, automation and "sent from the app" messages; pending/sent/failed states; reactions; redaction.
   - **Composer:** Enter to send, a 1,000-character counter, disabled reasons, and a 24 h window hint.
   - **Optimistic replies:**
     - A definitive 4xx denial puts the draft back in the composer with an inline error.
     - An ambiguous failure (network or 5xx) keeps a failed bubble whose "Try again" reuses the same idempotency key.
     - "Send again" on a server-failed message uses a new key, after confirmation when delivery is unconfirmed.
   - **Side panel:**
     - automation take over / hand back;
     - status actions per state;
     - assign / assign to me / unassign;
     - labels;
     - channel connection health with a link to diagnostics;
     - the customer card.
   - **Other behavior:**
     - Mark-read once per view for Operator and above (Q4).
     - `aria-live` announcement of new messages.
     - Viewer shows "View-only access".
     - Spam blocks the composer.
     - A 409 shows a refresh prompt.
     - 403 and 404 states.
6. **Real-backend Playwright suite (Q3: local, not in CI)** and a fixture-mode demo spec. Screenshots are listed below.

**Not done / deviations:**

- **D1 — window behavior.** The plan said a conversation outside the window "shows the composer disabled". Instead, the composer stays enabled with an explanatory hint, and the server's denial is shown inline.
  - Why: the client only knows the last customer message time. Whether a late reply is allowed is server/channel policy: HUMAN_AGENT eligibility, and a provider may accept or refuse.
  - The UI must not decide that fact (frontend rule: server is authoritative).
  - The real-backend spec asserts the hint, the denial copy, and that no outbound row was created.
- **D2 — old tests.** The fixture-coupled tests in `src/__tests__/inbox.test.tsx` were replaced. They exercised the old fixture-only page. Their behavior is now covered by `inbox-data.test.ts`, `inbox-ui.test.tsx` and the demo spec; the file keeps route-existence checks.
- **D3 — harness sign-in.** The real-backend harness signs each persona in once (global setup) and reuses the session cookies. The API's sign-in limiter allows 5 sign-ins per 15 minutes in total (see Known issues). The sign-in page itself is covered by existing auth tests; it is not repeated in this suite.

## Implementation design

- **Components/modules changed:**
  - Infrastructure: `BackgroundJobs/IntegrationJobs.cs` (registration + `HangfireIntegrationWorkScheduler`), `WebhookIngressService`, `ConversationReplyService`, `ConversationQueryService`.
  - Application: `IIntegrationWorkScheduler`, `ConversationContracts`.
  - WebApi: `ConversationsController`, `Program.cs`, `Seeding/E2eSeed.cs`, `DevSeedHook`.
  - Web: port, API and mock adapters, mapping, errors, the polling hook, `components/inbox/*`, both inbox pages.
- **Runtime or data flow:**
  1. A webhook is persisted, and the processing job is enqueued after commit. The minutely sweeper is the safety net.
  2. Processing ingests the message into the conversation.
  3. The UI polls `GET /v1/conversations[/{id}[/messages]]`.
  4. A reply POST creates the message and outbox entry atomically, and delivery is enqueued after commit.
  5. The job sends through the provider, and the next poll shows Sent or Failed with `deliveryFailureCode`.
- **Key invariants enforced:**
  - Scheduling never runs before commit and never throws into the request path. Failures are logged; the sweeper retries.
  - The UI never sets status, delivery state, or window facts.
  - Every write is server-authorized; UI role gating is cosmetic.
  - Demo mode uses a separate adapter that cannot reach the API. The demo spec asserts zero `/v1/` requests.
- **Compatibility with prior work:** API changes are additive. No migration. The scheduler is an optional constructor parameter, so existing tests and composition are unchanged.

## Security and isolation review

- **Authentication/authorization impact:**
  - The new route requires `conversations.read`.
  - All inbox writes stay server-authorized; Viewer write denial was verified end to end (403).
  - The UI role gating only mirrors the server.
- **Tenant-isolation impact:**
  - The assignee directory is filtered to active memberships of the resolved tenant.
  - An integration test proves another workspace's members are not returned and emails are not exposed.
  - The scheduler payload is the event/message ID only. The processing and delivery services load the persisted row by ID and act within its tenant (verified end to end by the real-backend suite).
- **Secret/PII/logging impact:**
  - No secrets committed.
  - The E2E harness generates random database, demo, simulator and master-key secrets per run, passes them only through process environment, and deletes the session-cookie temp directory on exit.
  - The E2E seed is Development-only and flag-gated.
  - Screenshots contain only synthetic personas and messages.
- **Abuse/idempotency/concurrency impact:**
  - Scheduling happens after commit and only for new work; duplicate execution is absorbed by existing per-event/per-message idempotency.
  - "Try again" reuses the idempotency key, so a retry after an ambiguous failure cannot create a second message.
  - "Send again" deliberately creates a new message, behind a confirmation when delivery is unconfirmed.
