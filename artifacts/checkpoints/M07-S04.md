- **Runtime or data flow:**
  1. Webhooks ingested in Step 03 are stored with status `Received`.
  2. `WebhookProcessingJob` executes periodically under Hangfire, using `ITenantJobRunner` to establish tenant context for each active tenant.
  3. Batch of `Received` or due `Failed` events are loaded and processed via `IWebhookProcessingService.ProcessWebhookEventAsync`.
  4. Event is marked `Processing`. Payload is normalized via `IChannelProvider.NormalizeInboundAsync`.
  5. For each envelope: schema version is validated (`v1`). If `ProviderMessageId` is present, deduplication checks ensure no duplicate `InboundEvent` is inserted.
  6. On success: `InboundEvent` records are saved and `WebhookEvent` is marked `Processed`.
  7. On transient failure: `WebhookEvent` is marked `Failed`, attempt count is incremented, and `NextRetryAt` is scheduled with exponential backoff + jitter. If `AttemptCount >= MaxAttempts`, it transitions to `DeadLetter` (`Exhausted`).
  8. On permanent failure (poison payload or unsupported schema): `WebhookEvent` is immediately quarantined to `DeadLetter` (`Permanent`).
  9. Operators can inspect DLQ via `GET /v1/integrations/webhooks/dead-letter` and trigger authorized idempotent replay via `POST /v1/integrations/webhooks/{id}/replay` with `Idempotency-Key`.
- **Key invariants enforced:**
  - **Two-Level Deduplication**: HTTP edge deduplication on `(ConnectionId, ProviderEventId)` from Step 03 plus message-level deduplication on `(ConnectionId, ProviderMessageId)` on `inbound_events`.
  - **Immutable Raw Reference**: Every `InboundEvent` has a foreign key to `WebhookEvent.Id`.
  - **Poison Event Quarantine**: Permanent failures do not consume retry cycles; they are quarantined immediately to DLQ.
  - **Bounded Exponential Backoff with Jitter**: Spreads out retries to avoid thundering herds.
  - **Strict Multi-Tenant Scoping**: All queries, background jobs, DLQ listings, and replay operations enforce verified tenant boundaries.
- **Compatibility with prior work:**
  - Additive EF Core migration with 0 pending model changes.
  - Preserves existing `WebhookEvent` records and `ChannelConnection` aggregate behavior.

## Security and isolation review

- **Authentication/authorization impact:** DLQ listing requires `IntegrationsRead`. Replay requires `IntegrationsWrite`, anti-forgery validation, and an `Idempotency-Key` header.
- **Tenant-isolation impact:** `WebhookProcessingJob` uses `ITenantJobRunner` to set tenant scope for each active tenant. All database operations on `WebhookEvents` and `InboundEvents` enforce tenant query filters. Cross-tenant processing or DLQ leakage is prevented.
- **Secret/PII/logging impact:** Secrets are never exposed. Errors stored in `ErrorMessage` are bounded and sanitized. Log messages use `[LoggerMessage]` source generators with masked identifiers.
- **Abuse/idempotency/concurrency impact:** Bounded retry attempts (default 5) and jitter prevent resource exhaustion. Poison events are quarantined immediately. Unique partial index on `(ConnectionId, ProviderMessageId)` rejects duplicate normalized messages. Concurrency token `xmin` prevents conflicting updates.

## Decisions and assumptions

- **ADRs created or changed:** Follows accepted `ADR-010` (connection ownership & routing), `ADR-011` (normalized events), `ADR-012` (payload retention & purge), and `ADR-013` (secrets encryption).
- **Assumptions made:** Jitter ratio is ±20% around nominal backoff intervals. Default max attempts is 5.
- **External evidence used:** Standard exponential backoff with full/equal jitter patterns.
