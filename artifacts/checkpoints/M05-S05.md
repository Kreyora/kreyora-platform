# M05-S05 Checkpoint — Public Storefront API and Resolution Boundary

**Status:** `REVIEW`

## Result

M05-S05 exposes the existing M05 quote, checkout-session, and canonical-order services through an anonymous, store-scoped API without allowing a browser to choose a tenant. An active, purchase-ready Store resolves only from one production subdomain label or the explicit Development/Testing route. The public surface is COD-only; merchant QR remains internal until real merchant configuration and proof handling exist.

No customer-facing Next.js journey, cart persistence, merchant QR checkout, seller order UI, custom-domain state machine, payment verification, notification, or M06 order operations were started.

## Scope completed

- Accepted ADR-009 and introduced a dedicated `PublicStorefrontContext`; it contains a verified tenant/store/slug tuple but no user, membership, role, or seller authority.
- Added public resolver middleware and marker metadata. Production accepts only `slug.platformBaseDomain`; Development/Testing also permits `/public/v1/dev/stores/{slug}`. Invalid, missing, inactive, unready, foreign, apex, multi-label, or malformed selections return one privacy-safe 404.
- Bound forwarded-host processing to explicitly configured proxy IPs. A direct client cannot use `X-Forwarded-Host` to select a Store.
- Added cacheable public profile/catalog/product/media projections. They return only active-store, visible-publication, published, purchasable facts; media is verified and streamed through private storage without exposing a bucket URL, object key, filename, tenant ID, Store ID, readiness state, or seller configuration.
- Added public quote, checkout-session, and canonical COD-order endpoints. The controller maps bounded public DTOs to existing authoritative services, requires an idempotency key for session/order writes, and never accepts payment method, totals, inventory, reservation, customer ID, Store ID, or tenant input.
- Reduced public write responses to safe DTOs: no delivery-rule ID, reservation ID, customer ID, checkout-session ID in order confirmation, storage details, or tenant/store fields.
- Corrected anonymous checkout-session audit provenance to `CommerceSystem`; COD readiness is now backed by an active zoned COD delivery rule instead of the prior unconditional payment placeholder.
- Added configurable cache TTL, 16 KiB public write limit, per-store/IP endpoint-family rate-limit partitions, `429` problem responses with `Retry-After`, `ETag`/`Vary: Host` reads, and `no-store` write/error responses.
- Regenerated the checked-in OpenAPI snapshot and TypeScript types from a live disposable Development API.

## Key invariants

| Invariant | Enforcement | Result |
|---|---|---|
| Browser cannot select a tenant | Resolver accepts host/dev route only; it opens the tenant scope after global active/readiness lookup | Pass |
| Public scope is not seller access | Context has no user/membership/role; seller authorization stays policy-based | Pass |
| Store data cannot leak across publication scope | Read projections require the resolved Store plus visible publication, published product, and purchasable variant | Pass |
| Public media stays private | Application verifies ready media → public product → resolved Store before opening private storage | Pass |
| Commerce remains authoritative | Quote/session/order adapters forward only intent to existing server services; COD is selected server-side | Pass |
| Anonymous provenance is honest | Checkout-session audit uses `CommerceSystem`, never a fabricated member | Pass |
| Public responses avoid operational IDs | Public response DTOs exclude tenant/store/customer, delivery-rule, reservation, and private-storage fields | Pass |
| Abuse limits do not use PII | Rate partition is endpoint family + verified store slug + remote IP | Pass |

## Reviewer procedure

1. Set `PublicStorefront__PlatformBaseDomain` to the real production platform base domain and `PublicStorefront__EnableDevelopmentSlugRoutes=false` outside Development/Testing. Configure only trusted reverse-proxy IPs in `PublicStorefront__TrustedProxyAddresses` when proxy host forwarding is used.
2. In Development/Testing, seed an active Store with contact/policy fields, a visible published purchasable product, available inventory, and a zoned active COD delivery rule.
3. Request `GET /public/v1/dev/stores/{slug}`, product/media routes, quote, session, and order routes. Verify public reads have ETag/cache headers, writes require `Idempotency-Key`, and only COD is accepted by the public order action.
4. Send tenant headers, Store IDs, totals, payment state, reservation IDs, or foreign product/session identifiers. They must not control the resolved Store or canonical commerce facts.
5. Inspect `PublicStorefrontController` response records: delivery-rule/reservation/customer/tenant/store/storage identifiers must not appear in the public response types.
6. Run the complete backend and frontend commands above with Docker available. Confirm Testcontainers cleanup after the run.
7. Approve M05-S05 to permit the deferred Graphify refresh and planning of M05-S06. Do not implement the M05-S06 UI before that approval.
