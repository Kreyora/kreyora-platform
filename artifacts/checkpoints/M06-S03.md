## Implementation Design

- **Components/modules changed:**
  - `Kreyora.Domain`: Added `OrderRestock` enum member and `PaymentAttempt.Expire`.
  - `Kreyora.Application`: Added `RestockForOrderAsync` to `IOrderInventoryReservationService` and corresponding DTOs.
  - `Kreyora.Infrastructure`: Implemented `RestockForOrderAsync` in `InventoryService` and orchestrated cancellation, restock, payment expiry, and outbox event publishing in `OrderOperationService`.
  - `Kreyora.IntegrationTests`: Created comprehensive PostgreSQL Testcontainers suite.
- **Runtime or data flow:**
  - **Checkout hold**: Reservation created (`Active`). `OnHand` unchanged, `Reserved` $+Q$, `Available` $-Q$.
  - **Order creation**: `OrderCreationService` calls `CommitForOrderAsync`: reservation committed, `OnHand` $-Q$, `Reserved` $-Q$, `ReservationCommitted` movement recorded.
  - **Fulfilment progression**: Order moves through `Confirm` -> `Prepare` (`Ready`) -> `Dispatch` (`Dispatched`) -> `Deliver` (`Delivered`). Stock remains allocated to order until delivery where ownership permanently transfers to customer.
  - **Cancellation**: Permitted from `PendingConfirmation`, `Confirmed`, `Ready`, or `Failed` (post-dispatch delivery failure). Calls `RestockForOrderAsync` which locks `InventoryItem`, increases `OnHandQuantity` ($+Q$), appends `StockMovementType.OrderRestock` ($+Q$), expires pending `PaymentAttempt`, appends `OrderCommand`, and emits `order.cancelled.v1` outbox event within a single serializable transaction.
- **Key invariants enforced:**
  - **Stock Ledger Balance**: Across every single terminal path, $\sum \text{StockMovement.QuantityDelta} = \text{InventoryItem.OnHandQuantity}$.
  - **Cancellation Restock**: Cancelled orders return all items to on-hand inventory with full audit and idempotency tracking.
  - **Dispatch Gate**: Orders with Merchant QR payment method cannot be dispatched until payment is verified (`PaymentStatus == Paid`).
  - **Transit Protection**: Dispatched orders cannot be cancelled directly; courier must report delivery failure first before cancellation/restock is permitted.
  - **Atomicity**: Order cancellation, stock restock, payment expiry, idempotency record, audit log, and outbox event execute in a single serializable transaction.

## Security and Isolation Review

- **Authentication/authorization impact:** All operations continue to enforce tenant authorization (`OrdersWrite` for operations, `PaymentsManage` for payments) via `ITenantPermissionAuthorizer`.
- **Tenant-isolation impact:** Inventory restock, row locks, movements, orders, payment attempts, and outbox messages are strictly scoped to `context.TenantId`.
- **Secret/PII/logging impact:** Audit logs record sanitized metadata; customer details are not exposed or logged.
- **Abuse/idempotency/concurrency impact:**
  - Idempotency verified: replaying duplicate cancellation commands returns `wasReplayed: true` and does not duplicate restock movements.
  - Concurrency verified: concurrent Cancel vs. Dispatch races serialize cleanly using PostgreSQL `xmin` concurrency tokens and row-level locks, returning safe conflict/denial responses.

## Decisions and Assumptions

- **Assumptions made:** Restocked items are returned to available on-hand balance unless damaged. If goods are damaged during delivery failure, the seller can record damage via existing stock adjustment (`Damage`) movements.
- **Outbox preparation:** Emitting outbox messages directly from `OrderOperationService` seamlessly sets up the foundation for Step 04 ("Notification outbox and development provider").
