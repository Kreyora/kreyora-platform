## Scope completed

Implemented `docs/plan/M09-S04_READ_TOOL_REGISTRY_PLAN.md` (approved 2026-10-06, "ok implement"; Q1–Q9 as recommended, Q6-A). Backend and API only; the console screen comes in S08. Nothing in this step calls a model.

1. **Registry** (`kreyora-read-tools.v1`):
   - a call runs only if the tool is registered, **is a read tool** and is **enabled in the shop's policy**; otherwise `tool_not_allowed`, and the tool is never invoked;
   - **strict argument schemas**: unknown fields such as `tenantId`, `priceNpr` or `stock` are rejected;
   - each call runs in **its own DI scope** in the context's tenant, under a **3-second deadline**;
   - failures come back as stable codes, never exceptions;
   - every call yields a JSON envelope for the model (`ok`, `tool`, `version`, `asOf`, `data` or `error`) plus a **values-free trace**.
2. **Trusted context:** tenant, store, conversation, customer identity, linked customer and allowed tools come **from the server** (tenant scope, conversation row, policy). The model's arguments are lookup keys only.
3. **Five read tools:** thin adapters over **three new customer-facing read queries**, which reuse the existing public-storefront, inventory, catalog and delivery data.
   - `ICustomerCatalogQuery`: exactly what the public storefront shows, with stock as bands;
   - `IDeliveryInfoQuery`: zone names at every level plus the gazetteer, server-priced items;
   - `IOrderStatusLookupService`: linked orders, or order number + last 4 phone digits with a lockout.
4. **Order-status protection:**
   - wrong pairs and unknown orders get the **same answer**;
   - **5 failures per order in 24 h lock chat lookups** of that order, even with the right digits (table `assistant_order_lookup_failures`);
   - failed and locked attempts are audited without the digits.
5. **Built-in Nepal gazetteer** (`NepalGazetteer`):
   - all 77 districts in English, Devanagari and common Romanized spellings;
   - 38 major cities mapped to their district;
   - "Kathmandu Valley" → ask which district.
6. **Storefront-link resolver** (`IProductReferenceResolver`, for S07; not a model tool):
   - exact match of links to **this shop's own** product pages (`https://{slug}.{base}/product/{p}` and `…/store/{slug}/product/{p}`);
   - never fetches a URL.
7. **Shared posts (Q6-A):**
   - the Instagram normalizer now keeps the first `*_id` field of a shared attachment as sent (for example `reel_video_id:…`), in the new `messages.shared_post_id` column;
   - redaction clears it;
   - no matching yet, until the S07 live capture.
8. **Owner console API:** `GET /v1/assistant/tools` (schemas, versions, enabled flags) and `POST /v1/assistant/tools/{name}/preview` (seller preview, no customer).
9. **Evaluation harness:** now offers the model the **real registry schemas**. Its fake inventory also reports bands instead of counts.

**Deviations from the plan:**
- **D1:** the ID pattern allows `-` and `_` (`^[0-9A-Za-z_-]{1,40}$`). Real IDs are ULIDs; the synthetic evaluation catalog uses IDs like `P-KURTA-RED`.
- **D2:** besides the lockout table, the migration adds `messages.shared_post_id`. The plan said "no change to message storage", but storing the identifier is the only way to keep it for the S07 matching.
- **D3:** the argument fingerprint in traces is an **HMAC with a per-process random key**, not a plain hash. A plain hash of 4 phone digits could be reversed.
- **D4:** product search runs the phrase plus up to 4 single words through the existing storefront search and ranks by matches, so "red kurta" finds "Red Cotton Kurta".

## Implementation design

- **Application:**
  - `Assistant/AssistantToolContracts.cs`: tool, registry, context, result, trace, error codes, console, product references;
  - query contracts appended to `Storefront/StorefrontContracts.cs` and `Orders/OrderContracts.cs`.
- **Domain:**
  - `Storefront/NepalGazetteer.cs`;
  - `Orders/OrderLookupGuard.cs`;
  - `Message.SharedPostId`; `MediaMessageReceivedPayload.SharedPostId`.
- **Infrastructure:**
  - `Assistant/Tools/`: `ToolSchemaValidator`, `AssistantToolRegistry`, `ReadTools` (the five tools), `AssistantToolServices` (context factory, console, link resolver);
  - `Storefront/CustomerCatalogQuery`, `Storefront/DeliveryInfoQuery`, `Orders/OrderStatusLookupService`.
- **Data flow:**
  1. S06 calls `IAssistantToolContextFactory.ForConversationAsync` (trusted context);
  2. `registry.GetDefinitions(context)` gives the tools offered to the model;
  3. per model tool call, `registry.ExecuteAsync`:
     - allowlist check;
     - schema validation;
     - new scope + tenant scope + deadline;
     - tool → read query (public-storefront scope for the store);
     - minimized result → envelope + trace.
- **Rules:** no business logic in the tools; queries never take a tenant from the caller; every ID is re-resolved under the tenant query filter **and** the store's publication state.

## Security and isolation review

- **Context:**
  - the tenant comes from the trusted scope;
  - store and customer come from the conversation row (tenant-checked);
  - allowed tools come from the policy.
  - The model can't supply tenant, price, stock or authorization: unknown fields are rejected, and prices for shipping come from the catalog.
- **Isolation:** every ID is re-resolved under the tenant query filter and the store's publication state; another tenant's IDs answer like missing ones (tested).
- **Minimization:**
  - no exact stock, PII, totals, SKUs, tenant IDs or hidden/draft products in any result (tested per tool);
  - traces and logs carry field names, outcome and a keyed fingerprint only.
- **Order-status abuse:**
  - two-factor knowledge (unguessable ULID order number + phone suffix);
  - uniform failure answer;
  - per-order lockout with audit.
  - [ASSUMPTION] Under heavy concurrent failures, a failed save is retried up to 3 times; if retries run out, that attempt answers `unavailable` (reveals nothing) rather than counting.
- **No SSRF:** link resolution never fetches; hosts are restricted to the platform domain (or development slug mode).
- **No model calls** and nothing sent to a provider in S04.

## Decisions and assumptions

- **ADRs:** none new. S04 adds no locked technology or provider; the registry follows ADR-018 data handling.
- [ASSUMPTION] Linking a chat customer to their orders (`CustomerChannelIdentity.CustomerId`) is not implemented. The linked-order path is tested by setting the link directly. S05 (checkout link from the chat) should create it.
- [ASSUMPTION] Production storefront links use `https://{slug}.{PlatformBaseDomain}/product/{slug}`. The current web app serves `/store/{slug}/product/{slug}`, and both are accepted.
- [UNRESOLVED] Which identifier Meta sends for shared posts and reels: verified in the S07 live session before matching is built (Q6-A).
