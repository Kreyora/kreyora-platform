## Invariant evidence

| Area | Result |
|---|---|
| Tampered public bodies | Extra tenant/store IDs, price/line/total/delivery/payment/publication fields cannot alter server-owned quote, session, or COD order facts. A foreign variant is rejected without leaking its ID. |
| Public isolation | Invalid host, missing slug, foreign checkout session, forged selector, and cross-store ETag cases stay isolated and privacy-safe. |
| Idempotency | Identical session retry returns replay; changed reuse conflicts; a second order key cannot create another order. |
| Last-unit contention | Two independent quotes/sessions for one unit yield one created session and one safe rejection; two order writes yield one order and one conflict. Persisted stock is reconciled. |
| Expiry | An expired order conflicts while the real `CheckoutSessionExpiryJob` expires/releases once. The second job run is idempotent and does not duplicate the expiry audit. |
| Immutable snapshots | Subsequent catalog title/variant price/name/publication and delivery-rule edits do not alter the canonical order/item totals or delivery snapshot. |

## Defect discovered and fixed

Concurrent public order creation could surface EF Core's transient-failure wrapper as a `400 Validation Error`. The invariant held—only one order persisted—but the HTTP error incorrectly implied invalid customer input.

- `InventoryService.CommitForOrderAsync` now lets transient `InvalidOperationException` failures escape as transient work rather than converting them to validation errors.
- `OrderCreationService` retries that transient failure with its existing bounded serializable retry policy; an exhausted retry budget returns the safe `409 Conflict` already used for checkout contention.
