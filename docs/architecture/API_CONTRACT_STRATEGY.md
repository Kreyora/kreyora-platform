# API Contract Strategy

## Overview

Kreyora uses a **typed contract boundary** between the Next.js frontend and the ASP.NET Core backend. The strategy separates transport-layer types (auto-generated from the OpenAPI spec) from frontend view-model types (hand-authored domain models).

## Type categories

| Category | Location | Source | Purpose |
|---|---|---|---|
| **Transport types** | `apps/web/src/lib/api/generated/` | Auto-generated by `openapi-typescript` from the live OpenAPI spec | Represent the exact shapes sent over the wire |
| **View-model types** | `apps/web/src/lib/types/` | Hand-authored | Frontend-optimised domain models used in components and hooks |
| **Port interfaces** | `apps/web/src/lib/ports/` | Hand-authored | Abstract client contracts consumed by hooks via `useClients()` |
| **Mock adapters** | `apps/web/src/lib/adapters/mock/` | Hand-authored | Fixture-data implementations of ports for demo mode |
| **API adapters** | `apps/web/src/lib/adapters/api/` | Hand-authored | Real HTTP implementations that call `apiFetch` and map transport types → view-model types |

## Data flow

```
Component → useClients() → Port Interface
                              ├── Mock Adapter → fixture data (demo mode)
                              └── API Adapter → apiFetch() → .NET API
                                                   ↕
                                          Transport types (generated)
                                                   ↕
                                          View-model types (mapped)
```

## Regenerating transport types

With the API running locally:

```bash
cd apps/web
pnpm generate:api
```

This reads `http://localhost:5001/openapi/v1.json` and writes `src/lib/api/generated/v1.ts`. The generated file is committed so CI can diff-check for drift.

## Adapter switching

The `ClientProvider` inspects the `NEXT_PUBLIC_API_URL` environment variable at runtime:

- **Set** → API adapters are used, real HTTP calls flow to the backend
- **Unset** → mock adapters are used, the app runs in demo mode with fixture data

This behaviour is controlled in `apps/web/src/lib/providers/client-provider.tsx`.

## Mapping convention

Each API adapter:

1. Calls `apiFetch<TransportType>(path)` using the generated transport type
2. Maps the transport response to the corresponding view-model type
3. Returns the view-model type to the port consumer

This keeps components decoupled from API shape changes — only the adapter mapping layer needs updating when the API evolves.

## Adding a new endpoint

1. Implement the controller/service in the .NET API
2. Regenerate types: `pnpm generate:api`
3. Create an API adapter in `apps/web/src/lib/adapters/api/` that maps the new transport type
4. Register the adapter in the `ClientProvider`'s API adapter set
