# API Contract Strategy

## Overview

Kreyora uses a **typed contract boundary** between the Next.js frontend and the ASP.NET Core backend. The strategy separates transport-layer types (auto-generated from the OpenAPI spec) from frontend view-model types (hand-authored domain models).

## Type categories

| Category | Location | Source | Purpose |
|---|---|---|---|
| **Transport types** | `apps/web/src/lib/api/generated/` | Auto-generated by `openapi-typescript` from the live OpenAPI spec | Represent the exact shapes sent over the wire |
| **View-model types** | `apps/web/src/lib/types/` | Hand-authored | Frontend-optimised domain models used in components and hooks |
| **Port interfaces** | `apps/web/src/lib/ports/` | Hand-authored | Abstract client contracts consumed by hooks via `useClients()` |
| **Mock adapters** | `apps/web/src/lib/adapters/mock/` | Hand-authored | Fixture-data implementations of ports for demo mode |
| **API adapters** | `apps/web/src/lib/adapters/api/` | Hand-authored | Real HTTP implementations that call `apiFetch` and map transport types → view-model types |

## Data flow

```
Component → useClients() → Port Interface
                              ├── Mock Adapter → fixture data (demo mode)
                              └── API Adapter → apiFetch() → .NET API
                                                   ↕
                                          Transport types (generated)
                                                   ↕
                                          View-model types (mapped)
```

## Regenerating transport types

With the API running locally:

```bash
pnpm generate:api
```

This downloads `http://localhost:5030/openapi/v1.json` into the committed `apps/web/src/lib/api/generated/openapi-v1.json` snapshot, then generates `v1.ts` from that snapshot. Set `KREYORA_OPENAPI_URL` to use a different OpenAPI document URL. The snapshot normalizes its non-contract `servers` URL to `http://localhost:5030/`; override that value only with `KREYORA_OPENAPI_SNAPSHOT_SERVER_URL`. Both generated files are committed so CI can diff-check for drift.

## Interactive API documentation

The API exposes its Development-only OpenAPI document at `/openapi/v1.json` and its interactive [Scalar](https://github.com/scalar/scalar) reference at `/scalar`. To use the local launch profile:

```bash
dotnet run --project services/api/src/Kreyora.WebApi/Kreyora.WebApi.csproj --launch-profile http
```

Open [http://localhost:5030/scalar](http://localhost:5030/scalar). Scalar reads the same `/openapi/v1.json` document used for contract generation. It is a local developer/reviewer convenience only: it is not mapped outside Development, requires no credential or provider configuration, and does not replace the committed OpenAPI snapshot or `pnpm generate:api` workflow.

## Adapter switching

The `ClientProvider` inspects the `NEXT_PUBLIC_API_URL` environment variable at runtime:

- **Set** → API adapters are used, real HTTP calls flow to the backend
- **Unset** → mock adapters are used, the app runs in demo mode with fixture data

This behaviour is controlled in `apps/web/src/lib/providers/client-provider.tsx`.

## Real-mode adapter rule

When `NEXT_PUBLIC_API_URL` is set, every completed backend capability must use its real API adapter. A failed real API call must show an error state; it must never silently fall back to fixture data. Fixture adapters remain only for modules whose backend capability has not been implemented in its scheduled milestone, and their UI must remain visibly identified as demo data.

Current state: browser authentication, including SMTP-backed password-reset request and confirmation, uses the real API in real mode. The reset request never returns a token or reset URL to the frontend; the user continues only from the email link. Workspace selection will move to the real tenant endpoints in M03-S05. Catalog, inventory, orders, inbox, storefront operations, payments, integrations, AI, billing, reporting, and audit views remain fixtures until their corresponding backend milestones provide the authoritative APIs.

## Mapping convention

Each API adapter:

1. Calls `apiFetch<TransportType>(path)` using the generated transport type
2. Maps the transport response to the corresponding view-model type
3. Returns the view-model type to the port consumer

This keeps components decoupled from API shape changes — only the adapter mapping layer needs updating when the API evolves.

## Adding a new endpoint

1. Implement the controller/service in the .NET API
2. Regenerate types: `pnpm generate:api`
3. Create an API adapter in `apps/web/src/lib/adapters/api/` that maps the new transport type
4. Register the adapter in the `ClientProvider`'s API adapter set
